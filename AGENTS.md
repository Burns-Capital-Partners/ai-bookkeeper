# Working on this starter

- Read README.md and docs/IMPLEMENTATION_GUIDE.md before implementation. Read the entity's private STATUS.md and confirmed context before asking repeated questions.
- Start with docs/START_HERE.md and docs/ENTITY_RECORD.md. Reuse the existing STATUS.md URL; keep it to about 200–300 words of completed/verified work and next actions. Maintain the linked one-page owner/CPA CONTEXT.md whenever facts or decisions change. Preserve lengthy evidence, technical instructions and old answers behind links, not in the running summary.
- Choose the smallest adaptation. This is a rental worker, not a general fund accounting platform. Keep Zoho as the official ledger.
- Never copy credentials, actual statements, personal data, live state, production config or old Git history into this repository. Use synthetic fixtures. Private configs and runtime files remain excluded.
- Preserve existing books and unrelated changes. No production posting, new schedule, irreversible migration, accounting-policy change or external message without applicable user authorization. Prepare concrete reviewable work before asking.
- Verify with npm test and npm run typecheck. Add meaningful regression coverage when changing financial controls, identity mapping, matching, recovery or schedules. A mock/test result is not live acceptance.
- Keep per-entity state, inputs, Drive folders and schedules separate. Check account overlap before allowing another writer in the same organization.
- Confirm the CPA's reporting basis and whether allocation is already applied. Current-year depreciation and accumulated depreciation are different checks. Unexplained balances remain questions until source records establish a cause.
- Keep one evidence-backed progress file in private entity storage. Lead the next authorized step; report only what remains. Never equate downloaded, staged, accepted, posted, reconciled and tax-final.
- Verify source reliability before legacy migration. Search all journal dates and check historical closing, new opening, target month and current balances after corrections; normal carryforward is not another opening entry.
- Batch factual questions and collection while access is usable; preserve dated account/use history and prior answers. Property-level reporting is the default, with detail retained where treatment requires it.
- Check the implementation guide's capability table before claiming support. P&L supports configured cash/accrual; registers/trial balance retain accrual ledger views. Supplemental accounts require explicit reviewed close evidence. Annual posting, additional feeds and tenant subledgers remain procedures/adaptations.
- Use docs/MONTHLY_CLOSE.md, docs/YEAR_END_CLOSE.md and docs/OPERATOR_GUIDE.md for continuing operations. Agree annual schedule preparation, posting and CPA review roles; never assume the accountant writes the entries.
- Close every material session with docs/CONTINUOUS_IMPROVEMENT.md: verify the shared entity update; promote useful generic lessons into actual checklists/code/tests; record the repo revision and separate deployment adoption. Never label an inaccessible or failed shared update as saved.
